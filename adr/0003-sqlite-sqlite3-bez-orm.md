# ADR-0003: Використання SQLite та пакету sqlite3 без ORM

- Статус: прийнято
- Дата: 2026-11-04
- Автор рішення:Токаренко Олександра

## Контекст і проблема:

Після етапу прототипування виникла потреба впровадити постійне сховище даних для проєкту. Необхідно забезпечити підтримку транзакцій для захисту від конфліктів при паралельних записах та реалізувати принцип розподілу відповідальності (Separation of Concerns), повністю відокремивши SQL-запити від бізнес-логіки.

## Фактори вибору:

- відсутність потреби розгортати окремий сервер БД:
- підтримка транзакцій та ACID;
- інкапсуляція роботи з даними через Repository Pattern;
- автоініціалізація схеми при запуску.

## Розглянуті варіанти:

- А. SQLite (sqlite3) без ORM.
- B. SQLite з ORM.
- C. PostgreSQL.

## Рішення:

Обрано варіант A: sqlite3 із патерном Repository. Транзакції захищено через BEGIN IMMEDIATE та обробку SQLITE_BUSY. Ініціалізація - у database/index.js.

## Плюси й мінуси варіантів:

А. SQLite (sqlite3) без ORM

- Плюс: локальний файл БД, повна підтримка транзакцій, легкість розгортання.
- Мінус: обмеження паралельного запису.

B. SQLite з ORM

- Плюс: менше ручної роботи з SQL, готові інструменти для міграцій.
- Мінус: з'являються зайві залежності; SQL ховається всередині бібліотеки, через що складні атомарні перевірки стає важче контролювати.

C. PostgreSQL

- Плюс: потужна реляційна БД, ідеальна для масштабування та складних запитів.
- Мінус: надлишкова складність та зайві витрати часу на налаштування інфраструктури.

## Наслідки:

- Позитивні: сервіси ізольовані від SQL; чіткий поділ відповідальності.
- Негативні: ускладнено керування з'єднаннями та транзакціями на рівні файлової БД.

## Як перевірено

Проведено комплексне тестування шару даних (`npm test`(працює на фейковому драйвері tests/helpers/fakeSqlite3.js, а справжню БД перевіряє check:http)): перевірено роботу транзакцій, механізм ретраїв при `SQLITE_BUSY`, атомарність бронювань та конкурентні запити.(скріншоти в DEFENSE).
