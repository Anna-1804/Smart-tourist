# ADR-0004: Мутаційне тестування: Stryker із command-runner

- Статус: прийнято
- Дата: 2026-11-11
- Автор рішення: Науменко Анна

## Контекст і проблема

Після написання unit- та інтеграційних тестів покриття гілок у `services/`, `middleware/` і `lib/`
становить 100%. Але покриття показує лише те, що рядок коду **виконався**, а не те, що його результат
**перевірено**: тест може пройти по всьому коду й не помітити зламаної умови чи порожнього повідомлення.
Потрібен спосіб знайти «зелені» тести, які не ловлять реальні помилки, і впорядковано їх класифікувати
(реальна прогалина / еквівалентний / прийнятний мутант).

## Фактори вибору

- об'єктивний і відтворюваний показник якості самих перевірок, а не лише виконання рядків;
- працює з уже написаними тестами на вбудованому `node --test`, без їх переписування;
- мінімум нових залежностей;
- звіт зі списком вижилих мутантів і зміною коду для кожного, щоб їх можна було класифікувати;
- прогін за розумний час на проєкті такого розміру.

## Розглянуті варіанти

- A. Лише покриття коду (звіт про покриття гілок).
- B. Stryker із універсальним `command`-runner (запускає весь `node --test` для кожного мутанта).
- C. Stryker зі спеціалізованим runner-плагіном під конкретний фреймворк.
- D. Ручний огляд тестів без інструменту.

## Рішення

Обрано **B**. Конфігурація `stryker.config.json`: команда `node --test "tests/**/*.test.js"`,
`coverageAnalysis: off`, область `services/`, `lib/`, `middleware/`, `concurrency: 2`. Запуск:
`npm run test:mutation`. Тести працюють на БД у пам'яті, тому паралельні прогони не заважають один одному.
Мутант, що завершився за таймаутом, вважається виявленим.

### Плюси й мінуси варіантів

**A. Лише покриття коду**

- Плюс: нічого не потрібно встановлювати, дуже швидко.
- Мінус: не перевіряє, чи тест щось стверджує про результат. У нашому проєкті при 100% покритті гілок
  було 16 вижилих мутантів, і саме покриття цього не показало.

**B. Stryker + command-runner**

- Плюс: працює з будь-яким способом запуску тестів, зокрема з вбудованим `node --test`, без плагінів.
- Плюс: дає HTML- та JSON-звіт із діфом для кожного вижилого мутанта.
- Мінус: без аналізу покриття по кожному тесту (`perTest`) кожен мутант проганяє весь набір, прогін
  триває близько 25 хвилин.

**C. Stryker + спеціалізований runner-плагін**

- Плюс: за наявності підтримки може пропускати тести, які не торкаються мутанта, і працювати швидше.
- Мінус: потрібен додатковий пакет і налаштування під конкретний фреймворк; для нашого `node --test`
  цей шлях не перевірявся.

**D. Ручний огляд тестів**

- Плюс: не потрібні інструменти.
- Мінус: суб'єктивно, не відтворюється, легко пропустити слабке місце.

## Наслідки

- Позитивні: знайдено 16 вижилих мутантів у коді зі 100% покриттям гілок; 8 з них були реальними
  прогалинами (рядок журналу завершення запиту, тексти відмов), їх закрито тестами. Після підсилення тестів
  score зріс з 95,17% до 98,33%. Мутаційний звіт також виявив тест, який загубився при злитті гілок.
- Негативні: повільний прогін, тому мутаційні тести не входять до `npm test` і `pre-push`, а запускаються
  окремо. Область не охоплює `repositories/` і `database/` (їх перевіряють інтеграційні тести на SQLite).
  Еквівалентні мутанти доводиться відсівати вручну.
- Ризик: після кожної зміни коду валідації з'являються нові мутанти, тому прогін треба повторювати перед
  здачею (так сталося після злиття виправлень: 331 → 419 мутантів, 8 нових прогалин).

## Як перевірено

`npm run test:mutation` → 419 мутантів, 399 убито, 13 за таймаутом, 7 вижили, mutation score 98,33%
(Stryker 10.1.1, коміт 64d3a41); `npm test` → 220 тестів зелені. Класифікація вижилих (5 прийнятних,
2 еквівалентні, 0 реальних прогалин): `docs/mutation-report.md`.
