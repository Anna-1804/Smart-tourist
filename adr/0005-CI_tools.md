# Інструменти CI: GitHub Actions, власна перевірка комітів, підсумкова перевірка ci-ok

- Статус: прийнято
- Дата: 2026-11-24
- Автор рішення: Токаренко Олександра

## Контекст і проблема

Після трьох робіт перевірки (форматування, лінт, тести) запускались лише локально через git-хуки, а хуки можна обійти (`--no-verify`). Потрібен CI, який перевіряє стиль, лінт, білд, тести й назви комітів на кожному Pull Request, і мердж у `main` заблоковано без зеленого результату.

## Фактори вибору

- репозиторій уже на GitHub, окремий сервер для CI не потрібен;
- мердж можна заблокувати вимогою обов'язкової перевірки;
- мінімум нових залежностей;
- одна й та сама перевірка комітів і в хуку, і в CI;
- зрозуміло, яка саме перевірка впала.

## Розглянуті варіанти

Платформа CI:

- A. GitHub Actions.
- B. GitLab CI.
- C. Jenkins.

Перевірка назв комітів (Conventional Commits):

- D. Власний скрипт `scripts/check-commits.js` без залежностей.
- E. commitlint із husky.
- F. Готова дія GitHub, що перевіряє лише назву PR.

## Рішення

Обрано A і D. Кожна перевірка (`style`, `lint`, `build`, `test`, `commits`, `docker`) це окремий job, щоб було видно, що саме впало. Підсумковий job `ci-ok` має `if: always()` і сам перевіряє результати інших; саме його вимагає захист гілки `main`.

### Плюси й мінуси варіантів

**A. GitHub Actions**

- Плюс: працює там, де вже лежить код; блокування мерджа вбудоване (обов'язкові перевірки в налаштуваннях гілки).
- Мінус: залежність від GitHub.

**B. GitLab CI**

- Плюс: зручні вбудовані пайплайни.
- Мінус: потрібно переносити репозиторій, команда працює в GitHub.

**C. Jenkins**

- Плюс: дуже гнучкий.
- Мінус: потрібен власний сервер і його підтримка, надмірно для навчального проєкту.

**D. Власний скрипт**

- Плюс: жодних нових пакетів; той самий код працює в хуку `commit-msg` і в CI; покритий тестами.
- Мінус: правила (типи комітів, довжину заголовка) підтримуємо самі; менше можливостей, ніж у commitlint.

**E. commitlint із husky**

- Плюс: стандартний інструмент, багато готових правил.
- Мінус: два нові пакети й зміна `package-lock.json` для однієї перевірки.

**F. Перевірка лише назви PR**

- Плюс: нічого не писати.
- Мінус: перевіряє назву PR, а не коміти, а ми зливаємо PR звичайним merge-комітом.

## Наслідки

- Позитивні: брудний PR не можна злити; кожну перевірку видно окремо; та сама перевірка комітів працює локально й у CI.
- Негативні: CI вимагає Node 22.8+ (файл `.nvmrc`, поле `engines`); job `docker` збирає образ на кожному PR, що довше.
- Ризик: job, пропущений через збій залежності, GitHub вважає успішним; тому в `ci-ok` результати залежностей перевіряються явно.
- Обмеження: коміти злиття й відкату (`Merge …`, `Revert …`) скрипт не перевіряє.

## Як перевірено

Локально: `npm test` (тести скрипта перевірки комітів входять до нього), перевірка назви коміта вручну (`fix stuff` дає код виходу 1, `fix: stuff` дає 0).

У CI: зелений прогін на PR `<посилання на PR>`; 5 навмисних порушень (форматування, лінт, білд, тест, назва коміта) дають червоні перевірки й заблоковану кнопку Merge (скріншоти в DEFENSE).
