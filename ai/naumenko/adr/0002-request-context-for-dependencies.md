# Керування залежностями: контекст запиту замість глобальних об'єктів

- Статус: прийнято
- Дата: 2026-11-04
- Автори рішення: Науменко Анна, Токаренко Олександра

## Контекст і проблема

Раніше `models/dbStore.js` одночасно перевіряв дані, виконував SQL і
повертав `{ success: false, status }`, який маршрут показував зі статусом 200.
БД бралась із глобального модуля `db.js`, роль адміна перевірялась прямо в
маршруті, а в логах не було способу зв'язати рядки одного запиту.
Потрібно відокремити сервісний шар (валідація, правила доступу) від шару
даних і передавати БД, користувача та ідентифікатор бізнес-процесу так, щоб
не тягнути їх параметрами через кожну функцію.

## Фактори вибору

- сервіси не знають про HTTP, репозиторії не знають про правила;
- кожен рядок логу має ID процесу без явного параметра в кожному виклику;
- БД можна підмінити (для тестів у наступній роботі);
- мінімум нових npm-залежностей;
- помилки мають мати HTTP-статус (400/403/404/409/500).

## Розглянуті варіанти

- A. Глобальні об'єкти (поточний стан: `require('./db')` у `dbStore.js`).
- B. Передавати `db`, `user`, `processId` параметрами в кожну функцію.
- C. Контекст запиту на `AsyncLocalStorage` (вбудований модуль Node.js).
- D. DI-контейнер (сторонній пакет).

## Рішення

Обрано **C**. Middleware `requestContext` створює `{ db, user, processId }` на
кожен запит; репозиторії беруть БД із контексту, правила доступу беруть
користувача з контексту, логер додає `[process=ID]` до кожного рядка.
Разом з цим: репозиторії працюють на Promise (SQL без валідації), сервіси
кидають помилки з полем `status`, один `app.use((err, req, res, next))`
перетворює їх на відповідь.

### Плюси й мінуси варіантів

**A. Глобальні об'єкти**

- Плюс: найпростіше, нічого міняти.
- Мінус: немає ID процесу в логах; БД і користувача важко підмінити;
  валідація, правила й SQL лишаються в одному місці.

**B. Параметри в кожну функцію**

- Плюс: залежності явні, нічого «магічного».
- Мінус: підписи функцій обростають `db, user, processId`; кожен виклик
  логера теж має отримувати ID; багато механічних змін.

**C. AsyncLocalStorage**

- Плюс: вбудований модуль, без нових залежностей.
- Плюс: ID процесу й користувач доступні будь-де в ланцюжку запиту.
- Плюс: БД легко підмінити в контексті.
- Мінус: залежності неявні, функція без контексту працює лише завдяки
  запасному варіанту (`db.js`).
- Мінус: контекст може загубитись у колбеках драйвера, тому репозиторії
  обгортають запити в Promise, а події на кшталт `res.on('finish')`
  відновлюють контекст вручну.

**D. DI-контейнер**

- Плюс: явне керування життєвим циклом залежностей.
- Мінус: нова залежність і складність, надмірна для проєкту цього розміру.

## Наслідки

- Добре: кожен рядок логу має `[process=ID]`; той самий ID повертається
  в заголовку `X-Process-Id`; помилки мають правильні статуси замість 200.
- Добре: сервіси, репозиторії й обробка помилок розділені між двома
  учасницями без конфліктів у файлах.
- Погано: неявні залежності складніше відстежувати; старий `dbStore.js`
  і його юніт-тести лишаються до третьої роботи, де їх буде перероблено.
- Ризик: у кодах, що викликаються поза запитом, контексту немає
  (логер пише `process=-`).

## Як перевірено

`curl -i` для сценаріїв помилок дав статуси 400/403/404/409; у консолі
сервера рядки одного запиту мають однаковий `[process=…]`, який збігається
з `X-Process-Id` у відповіді.

Довідка: https://nodejs.org/api/async_context.html
