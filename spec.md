# Специфікація проєкту

## 1. Архітектура

Ланцюжок взаємодії:
Routes → Services → Repositories → SQLite

- **routes** знають лише про HTTP(розбір запиту, статус, redirect)
- **services** — бізнес-правила: валідація, права доступу, рішення про 404/409;
- **repositories** — увесь SQL і транзакції, які виконують запити через обгортку (base.js) та беруть підключення до бази даних безпосередньо з контексту запиту;
- **контекст запиту** (`AsyncLocalStorage`): глобальне сховище (context.js), що зберігає активне підключення до БД, об'єкт користувача з роллю та унікальний ідентифікатор процесу (processId) для кожного окремого запиту;
- **логер** (`logger.js`): втоматично витягує processId із контексту запиту й додає мітку [process=ID] до кожного рядка логування (info, warn, error);
- **один глобальний обробник помилок** (400/403/404/409/500); сервіси й репозиторії просто кидають помилки.

## 2. Cхема БД

![Cхема БД](./images/Node.js_lab2.drawio.png)

- cities(id, name, description)
- tours(id, city_id, title, description, program, price, available_slots ≥ 0, image_url)
- bookings(id, tour_id, user_name, user_email, slots_booked > 0, created_at, idempotency_key UNIQUE)
- reviews(id, tour_id, user_name, rating 1..5, comment, created_at)
  created_at — ISO YYYY-MM-DD HH:MM:SS (UTC). Каскадне видалення, PRAGMA foreign_keys = ON.

## 3. Прототип і HTTP-інтерфейс

Спершу сценарії працюють на статичних даних, а потім на SQLite.

| Сценарій                      | Запит                        | Результат                                             |
| ----------------------------- | ---------------------------- | ----------------------------------------------------- |
| 1.1.Пошук за містом           | GET /?city_id=               | 200, список турів                                     |
| 1.2.Деталі туру               | GET /tours/:id               | 200 / 404                                             |
| 1.3.Бронювання                | POST /tours/:id/book         | 200 (сторінка туру з повідомленням) / 400 / 404 / 409 |
| 1.4.Відгук                    | POST /tours/:id/reviews      | 200 / 400 / 404                                       |
| 2.1.Новий тур                 | POST /admin/tours            | 200 / 400 / 403                                       |
| 2.2.Зміна туру                | POST /admin/tours/:id/update | 200 / 400 / 403 / 404                                 |
| 2.3, 2.4.Відгуки і бронювання | GET /admin                   | 200 / 400 /403                                        |

### Сценарії для користувача:

_**Сценарій 1.1: Вибір міста та пошук екскурсій**_

**Кроки:**

1. Користувач переходить на головну сторінку або сторінку вибору міст та обирає конкретне місто зі списку чи через пошук.
2. Сервер обробляє запит і здійснює пошук доступних екскурсій для цього міста.
3. Сервер формує готову HTML-сторінку зі списком знайдених турів та відправляє її у браузер.

**Очікуваний результат:** Користувач бачить візуально привабливий список екскурсій, які проводяться саме у вибраному місті, з їхніми назвами, фотографіями та цінами.

_**Сценарій 1.2: Перегляд детального опису екскурсії**_

**Кроки:**

1. Користувач клікає на картку конкретної екскурсії зі списку для перегляду детальної інформації.
2. Сервер збирає повну інформацію про обраний тур (опис, програму, ціну, доступні місця), а також підтягує пов'язані з ним відгуки.
3. Сервер рендерить детальну сторінку туру та відображає її у браузері.

**Очікуваний результат:** Користувач отримує повний огляд екскурсії: розгорнутий опис, програму поїздки, вартість, кількість вільних місць та список реальних відгуків інших туристів.

_**Сценарій 1.3: Бронювання місць на екскурсію**_
**Кроки:**

1. Користувач на сторінці детального перегляду екскурсії заповнює форму бронювання (вказує своє ім'я, email та кількість місць) і натискає кнопку «Забронювати».
2. Сервер приймає та перевіряє введені дані й наявність достатньої кількості вільних місць.
3. Система фіксує бронювання та зменшує лічильник доступних місць на екскурсії, після чого перенаправляє користувача назад на сторінку туру з повідомленням про успіх.

**Очікуваний результат:** Місця успішно заброньовані, кількість вільних місць на екскурсії автоматично зменшилась, а користувач бачить підтвердження про успішне оформлення поїздки.

_**Сценарій 1.4: Залишення відгуку про поїздку**_
**Кроки:**

1. Користувач на сторінці конкретного туру заповнює форму відгуку (оцінка від 1 до 5 та текст коментаря) і натискає «Надіслати».
2. Сервер приймає та перевіряє коректність оцінки й коментаря, а потім зберігає відгук у системі.
3. Сервер робить перенаправлення користувача назад на сторінку цього ж туру.

**Очікуваний результат:** Сторінка оновлюється, і новий відгук користувача з'являється у загальному списку відгуків на сторінці екскурсії.

### Сценарії для адміністратора:

_**Сценарій 2.1: Додавання нових екскурсій**_
**Кроки:**

1. Адмін заповнює форму створення туру (назва, опис, програма, ціна, доступні місця, місто тощо) у панелі керування та надсилає дані.
2. Сервер зчитує та перевіряє передані дані, після чого створює новий запис про екскурсію в системі.
3. Сервер робить перенаправлення адміна на оновлену сторінку зі списком усіх турів.
   **Очікуваний результат:** Нова екскурсія успішно додана до системи і одразу з'являється у загальному каталозі платформи для пошуку користувачами.

_**Сценарій 2.2: Керування розкладом**_
**Кроки:**

1. Адмін обирає екскурсію для редагування, змінює параметри розкладу чи доступних місць у спеціальній формі та надсилає запит на оновлення.
2. Сервер зчитує оновлені дані та перезаписує відповідну інформацію в системі.
3. Після успішного оновлення сервер перенаправляє адміна на сторінку управління екскурсіями.

**Очікуваний результат:** Розклад або параметри екскурсії успішно оновлені в системі, і користувачі бачать актуальну інформацію на сайті.

_**Сценарій 2.3: Аналіз відгуків**_
**Кроки:**

1. Адмін переходить у розділ аналізу відгуків або відкриває сторінку конкретної екскурсії для перевірки зворотного зв'язку.
2. Сервер збирає всі відгуки, залишені користувачами для цього туру.
3. Сервер формує і виводить в адміністративну панель зведений список відгуків.

**Очікуваний результат:** Адміністратор бачить повну картину оцінок та коментарів від туристів, що дозволяє оцінити якість проведення екскурсії.
**Критерій:** адмін бачить відгуки, відфільтровані за туром: `GET /admin?tour_id=N` показує відгуки лише туру N; без параметра `tour_id` показано всі відгуки; нечисловий або недодатний `tour_id` дає відповідь 400.

_**Сценарій 2.4: Перевірка статусу бронювань**_
**Кроки:**

1. Адмін відкриває розділ перегляду всіх бронювань або бронювань конкретного туру в адмін-панелі.
2. Сервер формує актуальний перелік усіх оформлених бронювань із прив'язкою до екскурсій.
3. Система виводить список туристів, їхні контакти та кількість зайнятих місць.

**Очікуваний результат:** Адміністратор має повну інформацію про те, хто і скільки місць забронював на ту чи іншу екскурсію, що допомагає в організації поїздок.
**Критерій:** адмін бачить бронювання, відфільтровані за туром: `GET /admin?tour_id=N` показує бронювання лише туру N; без параметра `tour_id` показано всі бронювання; нечисловий або недодатний `tour_id` дає відповідь 400.

## 4.SQL-запити

### Сценарії користувача.

_**1.1 Вибір міста та пошук екскурсій.**_

Якщо місто не обране, повертаються всі тури.

<pre><code>SELECT t.*, c.name AS city_name FROM tours t LEFT JOIN cities c ON c.id = t.city_id WHERE (? IS NULL OR t.city_id = ?) ORDER BY t.id;</code></pre>

_**1.2 Перегляд опису екскурсій.**_

Інформація про екскурсію разом з містом:
<pre><code>SELECT t.*, c.name AS city_name FROM tours t LEFT JOIN cities c ON c.id = t.city_id WHERE t.id = ?;</code></pre>

Відгуки цієї екскурсії:
<pre><code>SELECT * FROM reviews WHERE tour_id = ? ORDER BY datetime(created_at) DESC, id DESC;</code></pre>

_**1.3 Бронювання місць.**_
<pre><code>SELECT * FROM bookings WHERE idempotency_key = ?;

UPDATE tours
SET available_slots = available_slots - ?
WHERE id = ? AND available_slots >= ?;

INSERT INTO bookings
(tour_id, user_name, user_email, slots_booked, created_at,idempotency_key)
VALUES (?, ?, ?, ?, ?, ?);</code></pre>

_**1.4 Залишення відгуку.**_
<pre><code>INSERT INTO reviews (tour_id, user_name, rating, comment, created_at) VALUES (?, ?, ?, ?, ?);</code></pre>

### Сценарії адміністратора.

_**2.1 Додавання нової екскурсії.**_
<pre><code>INSERT INTO tours (city_id, title, description, program, price, available_slots, image_url) VALUES (?, ?, ?, ?, ?, ?, ?);</code></pre>

_**2.2 Зміна екскурісії.**_
<pre><code>UPDATE tours SET title = COALESCE(?, title), description = COALESCE(?, description), program = COALESCE(?, program), price = COALESCE(?, price), available_slots = COALESCE(?, available_slots), image_url = COALESCE(?, image_url) WHERE id = ?;</code></pre>

_**2.3 Аналіз відгуків.**_
<pre><code>SELECT r.*, t.title AS tour_title FROM reviews r LEFT JOIN tours t ON t.id = r.tour_id
WHERE (? IS NULL OR r.tour_id = ?) ORDER BY datetime(r.created_at) DESC, r.id DESC;</code></pre>

_**2.4 Перевірка бронювань**_
<pre><code>SELECT b.*, t.title AS tour_title FROM bookings b LEFT JOIN tours t ON t.id = b.tour_id
WHERE (? IS NULL OR b.tour_id = ?) ORDER BY datetime(b.created_at) DESC, b.id DESC;</code></pre>

## 5. Сценарії помилок

|  №  | Ситуація                  | Очікувана поведінка                                                          |
| :-: | :------------------------ | :--------------------------------------------------------------------------- |
| 1.  | Місць менше, ніж просять  | 409, бд не змінюється                                                        |
| 2.  | Порожні обов'язкові поля  | 400, дані не записуються                                                     |
| 3.  | Некоректні дані           | 400 з поясненнями                                                            |
| 4.  | Неіснуючий тур/маршрут    | 404                                                                          |
| 5.  | Не адмін                  | 403                                                                          |
| 6.  | Збій або недоступність Бд | 500                                                                          |
| 7.  | Паралельні бронювання     | транзакції йдуть по черзі; зайві запити отримують 409, сервер не зупиняється |
| 8.  | Повторне надсилання форми | redirect після POST + idempotency_key: друге бронювання не створюється       |
| 9.  | Тимчасовий SQLite_Busy    | до 3 повторів транзакції з паузою; нетимчасові помилки не повторюються       |
